Week 1 · Day 4 · Retries & timeouts

Retries & timeouts: bila send betul² fail?

Ada empat setting: retries, retry.backoff.ms, request.timeout.ms, delivery.timeout.ms. Tapi cuma satu je yang betul² cakap "dah, fail". Yang mana satu?

Teka dulu (30 saat): retries=0. Broker kena restart 5 saat, lepas tu hidup balik. Record yang dihantar masa tu hilang ke tak? Tulis jawapan dulu, baru scroll.

1. Empat setting, empat tugas

Dari lesson 0002: NotEnoughReplicas tu retriable, dan producer retry sampai delivery.timeout.ms habis. Sekarang kita bedah mekanisme tu:

SettingDefaultTugas dia
request.timeout.ms30 stunggu satu response je. Habis masa → request tu dianggap gagal.
retry.backoff.ms / retry.backoff.max.ms100 ms / 1 sberapa lama rehat sebelum cuba lagi. Naik eksponen sampai max.
retries2147483647had bilangan cubaan semula
delivery.timeout.ms120 s (Java) · 300 s (librdkafka)jam total satu record, dari send() sampai ack atau error

Default retries tu hampir tak terhingga. Maksudnya dia hampir tak pernah jadi penentu. Kafka docs sendiri cadangkan: biar retries macam tu, dan kawal guna delivery.timeout.ms je. (retries · delivery.timeout.ms · request.timeout.ms · backoff · librdkafka CONFIGURATION.md)

Jawapan teka-teka: dengan retries=0, error transient tak di-retry. Docs retries tulis: "transient errors will be propagated to the application". Jadi record yang kena masa broker restart fail terus ke callback, walaupun broker hidup balik 5 saat lepas tu. Hilang, tapi bukan senyap: ko dapat error. (RETRIES_DOC)

Awas, Java ≠ librdkafka. Edge ko guna librdkafka (Python). Kat sana request.timeout.ms ialah ack timeout sebelah broker ("only enforced by the broker"), bukan berapa lama client tunggu response. Had tunggu network sebelah client ialah socket.timeout.ms (default 60 s). Dan message.timeout.ms (= delivery.timeout.ms) liputi retry sekali. Error keluar bila retry count atau message timeout habis, mana dulu. Rajah kat bawah ikut semantik Java. (librdkafka CONFIGURATION.md)

2. Satu record, satu jam

Jam delivery.timeout.ms start bila send() dipanggil. Docs Java: dia had jumlah masa record tertangguh sebelum hantar, tunggu ack, dan retry. Jam ni jalan terus walaupun ada backoff. Tengok apa jadi bila broker "senyap" (TCP sambung tapi tak balas), semantik Java: (DELIVERY_TIMEOUT_MS_DOC)

Kalau broker menolak sambungan terus (bukan senyap), setiap cubaan fail dalam milisaat, dan backoff yang tentukan berapa banyak cubaan muat. Backoff mula 100 ms, didarab 2 setiap kali, dengan jitter 20%, dan dihadkan 1 s. (CommonClientConfigs) Dalam dua-dua kes, pada default yang potong akhirnya ialah delivery.timeout.ms, bukan retries. Producer boleh fail lebih awal kalau jumpa error tak boleh pulih, retries habis (cth retries=0), atau record masuk batch yang deadline-nya lagi awal.

3. Kenapa delivery.timeout.ms ≥ linger.ms + request.timeout.ms

Soalan roadmap. Record kena duduk dalam batch sampai linger.ms habis, lepas tu hantar, dan tunggu response sampai request.timeout.ms. Itu satu cubaan yang paling kurang. Kalau delivery.timeout.ms lagi kecil dari jumlah tu, record boleh expired sebelum broker sempat jawab, dan producer langsung tak dapat peluang betul². Java enforce ni masa construct producer: kalau ko set sendiri delivery.timeout.ms lebih kecil, dia baling ConfigException. Kalau ko tak set tapi naikkan request.timeout.ms sampai jumlah melepasi 120 s, dia senyap² naikkan delivery.timeout.ms dan cuma log warning. (configureDeliveryTimeout)

Default: 5 + 30000 = 30005 ms minimum. Default sebenar 120 s bagi ruang lebih kurang 4 cubaan penuh.

Satu lagi tie-in dengan 0002: docs Java cadang request.timeout.ms lebih besar dari replica.lag.time.max.ms (30 s) supaya producer tak retry sebab follower lambat, kerana retry macam tu boleh jadi duplicate. Default dua-dua 30 s, so tak lebih besar pun. (REQUEST_TIMEOUT_MS_DOC)

4. Retriable vs tak retriable

  • Retriable (producer cuba lagi): NotEnoughReplicas, NotLeaderOrFollower (leader pindah), network error, request timeout.
  • Tak retriable (fail terus, tak tunggu jam): MessageTooLarge, authorization error. Retry seribu kali pun jawapan sama.

Sebab tu config salah macam topic tak wujud atau ACL salah selalu fail cepat, manakala broker down fail lambat (tunggu jam habis).

5. Request timeout: hasil yang tak pasti

Ni jebakan sebenar. Bila request.timeout.ms habis, producer tak tahu broker dah tulis record tu ke belum. Mungkin request tak sampai langsung. Mungkin broker dah tulis, cuma response tersangkut. Producer retry dalam dua-dua kes, jadi dalam kes kedua, record masuk dua kali.

Inilah sebab retry tanpa idempotence boleh bagi duplicate dan, kalau ada beberapa request in flight, boleh salah susun. Day 5 kita bedah penyelesaiannya (producer ID + sequence number). Untuk sekarang, ingat: retry selamatkan record daripada hilang, tapi bukan percuma.

Edge ko

edge-producer.properties set delivery.timeout.ms=120000 (dari lesson 0001). Maksudnya outage broker atau link yang lebih lama dari 2 minit mula buang record tertua dulu. Satu angka ni tentukan "berapa lama edge boleh tahan" untuk masalah pendek. Untuk outage WAN yang lagi lama, kita bincang buffering di Week 4.

7. Lab preview 💻 desktop only

Guna lab 3-broker, BUKAN node edge production. Tulis ramalan dulu: berapa lama sampai callback pertama dapat error?

cd ~/workspaces/kafka-in-depth
python clients/producer.py -t orders -n 0 -r 5 \
  -X delivery.timeout.ms=20000 &
podman stop kafka-1 kafka-2 kafka-3     # semua broker mati
# catat masa sampai on_delivery lapor error
podman start kafka-1 kafka-2 kafka-3
Check ramalan

Lebih kurang 20 s selepas record dihantar, ikut delivery.timeout.ms (= message.timeout.ms dalam librdkafka), bukan retries yang default 2147483647. Kalau ko tukar delivery.timeout.ms=60000 dan ulang, masa tu ikut jadi ~60 s. Kalau error datang lebih awal dari tu, check mesej: mungkin bukan retriable.
