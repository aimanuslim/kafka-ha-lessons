Retries & timeouts

Empat setting yang nampak macam semua tentang "bila send fail", tapi cuma satu yang betul² tentukan. Disemak dengan source Kafka 4.1 (ProducerConfig) dan librdkafka master (CONFIGURATION.md).

Siapa buat apa

SettingKawal
delivery.timeout.msjam total satu record. Tamat = record fail (jalan B). Ni yang tentukan bila send fail.
request.timeout.msberapa lama client tunggu satu response. Tamat = request dianggap gagal, retry kalau masa masih ada.
retry.backoff.ms / .max.msjeda antara retry (naik eksponen sampai max)
retrieshad bilangan retry. Default hampir tak terhingga, so jarang jadi penentu.

Peraturan

  • Java: delivery.timeout.ms ≥ linger.ms + request.timeout.ms. Kalau ko set sendiri dan lebih kecil → ConfigException. Kalau ko tak set → Java naikkan sendiri + warning.
  • retries=0 → error transient terus ke app. Producer juga fail awal kalau error tak boleh pulih atau retries habis.
  • Backoff: mula 100 ms, ×2, jitter 20%, had 1 s.
  • librdkafka: error bila retry count atau message.timeout.ms habis, mana dulu.
  • Retriable (retry): NotEnoughReplicas, NotLeaderOrFollower, network error, request timeout.
  • Non-retriable (fail terus): MessageTooLarge, authorization error, dan sebagainya.
  • Docs Java cadang request.timeout.ms > replica.lag.time.max.ms (30 s), supaya kurang retry/duplicate yang tak perlu.
  • Request timeout = hasil tak pasti. Broker mungkin dah tulis. Retry boleh duplicate, melainkan idempotence on (Day 5).
  • Cara tune yang disyorkan: biar retries default, set delivery.timeout.ms ikut berapa lama ko sanggup tunggu.

Formula pantas

Minimum delivery.timeout.ms = linger.ms + request.timeout.ms.
Default: 5 + 30000 = 30005 ms. Default sebenar 120000 ms muat lebih kurang 4 cubaan penuh kalau broker senyap.
